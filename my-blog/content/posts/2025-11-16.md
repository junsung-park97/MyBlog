기존 서비스에 **다수의 클라이언트와 AI Agent가 동시에 참여하여 여행 일정을 협업할 수 있는 기능**을 추가하게 되었습니다.

대략적인 요구사항 다음과 같습니다.

- 특정 여행의 참가자는 채팅을 통해 실시간 소통할 수 있습니다.
- 참가자는 지도에 마킹(핀)을 추가 할 수 있습니다.
- 지도에 추가된 마킹(핀)은 모든 참가자에게 실시간으로 공유할 수 있습니다.
- 참가자는 여행 일정을 추가, 수정, 삭제 할 수 있습니다.
- 일정내용은 모든 참가자에게 실기간으로 동기화되어야 합니다.

해당 아티클은 기존의 **HTTP 기반 통신 구조**가 위와 같은 요구사항을 충족하는 데 왜 한계가 있는지 살펴보고, WebSocket의 통신 구조와 동작 원리를 분석합니다. 또한 이러한 통신 구조를 실제 프로젝트에 어떻게 적용했는지, 그리고 그 과정에서 얻은 기술적 인사이트를 공유합니다.

## 1. HTTP 통신이 실시간 통신에 적합하지 않은 이유

### 1-1. HTTP의 근본적 제약: 클라이언트-주도 요청-응답 모델

HTTP는 클라이언트-주도 요청-응답 모델을 기반으로 하는 단방향 통신 프로토콜입니다. 클라이언트가 요청을 보내면 서버가 응답하는 구조로, 서버가 능동적으로 클라이언트에게 데이터를 전송할 수 없습니다. 이는 **요청 없이는 응답 없다**는 HTTP의 핵심 원칙에서 비롯됩니다.

실시간 협업 환경에서는 한 사용자의 변경사항을 다른 사용자에게 즉시 전달해야 합니다. 하지만 HTTP에서는 서버가 변경사항을 감지하더라도 클라이언트의 요청이 없으면 알릴 방법이 없습니다. 이러한 제약으로 인해 HTTP는 실시간 통신에 근본적으로 부적합합니다.

### 1-2. Polling 방식의 한계

HTTP의 제약을 우회하기 위해 Polling 방식을 사용할 수 있지만, 여러 문제점이 있습니다.

**Short Polling**은 클라이언트가 주기적으로 서버에 변경사항을 요청하는 방식입니다. 1초마다 요청하는 경우 최대 1초의 지연이 발생하여 실시간성이 떨어지며, 변경사항이 없어도 계속 요청을 보내 불필요한 네트워크 트래픽과 서버 부하를 발생시킵니다.

**Long Polling**은 서버가 변경사항이 발생할 때까지 응답을 대기하는 방식으로 Short Polling보다 효율적입니다. 하지만 여전히 각 요청마다 새로운 HTTP 연결을 생성하고 종료해야 하며, 서버는 대기 중인 요청을 유지하기 위해 자원을 소모합니다. 또한 HTTP의 무상태(Stateless) 특성으로 인해 매 요청마다 인증 정보를 포함한 전체 헤더를 전송해야 하는 오버헤드가 발생합니다.

이러한 이유로 실시간 협업 기능 구현에는 WebSocket과 같은 양방향 통신 프로토콜이 필요합니다.

## 2. Web Socket의 정의와 원리 그리고 기술적 도전과제

### 2-1. Web Socket의 정의와 통신구조

Web Socket은 클라이언트와 서버간에 **실시간, 양방향 상호작용**을 가능하게 하는 통신 프로토콜입니다. HTTP와 달리 연결이 유지되는 상태에서 데이터를 주고받을 수 있으며, 다음과 같은 특징을 가지고 있습니다.

- **풀 듀플렉스(Full-Duplex)** : 클라이언트와 서버가 마치 전화통화와 같이 동시에 데이터를 주고 받을 수 있습니다.
- **이벤트 기반 (Event-driven)** : HTTP 요청 - 응답 모델과 달리, 이벤트가 발생하면 데이터 흐름이 트리커되는 방식으로 작동됩니다.
- **지속적인 연결** : 한 번 연결이 수립되면, 세션이 끝날 때 까지 연결이 유지되어 반복적인 연결 설정 오버헤드가 없습니다.
  이러한 특성 덕분에 Web Socket은 채팅, 실시간 협업, 온라인 게임과 같은 실시간 어플리케이션에 거의 필수적으로 사용됩니다.

### 2-2. WebSocket연결의 작동원리:핸드셰이크부터 데이터 전송

#### 1단계 : 초기 HTTP요청

클라이언트는 WebSocket 연결을 시작하기 위해 다음과 같은 특수 헤더를 포함한 표준 HTTP요청을 보냅니다.

```http
GET /Chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key
Sec-WebSocket-Version: 13
```

이때 `Upgrade: websocket`, `Connection: Upgrade`헤더를 포함하여 WebSocket 연결을 요청합니다.

#### 2단계 : 서버응답

서버가 WebSocket을 지원하고 연결을 수락하면 다음과 같이 응답합니다.

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: Authentication HASH_VALUE
```

성공적인 프로토콜 업그레이드를 확인하는 상태코드 `HTTP/1.1 101 Switching Protocols`로 응답하여 프로토콜 업그레이드를 승인합니다. 이때 서버는 클라이언트 키를 해시한 `Sec-WebSocket-Accept`헤더를 포함하여 응답합니다.

#### 3단계 : 지속적인 연결 확립 및 데이터 전송

프로토콜 업그레이드가 완료되면, HTTP 연결은 **TCP 기반의 풀 듀플렉스(Full Duplex) WebSocket 연결**로 전환되며 열린 상태를 유지합니다. 이후 데이터는 통신의 기본 단위인 **프레임(Frame)** 을 통해 양방향으로 전송됩니다.

#### 4단계 : 연결 종료

연결을 종료할 때는 어느 한쪽이 **종료 프레임(Close Frame)** 을 전송할 수 있으며, 이 프레임에는 종료 사유를 나타내는 상태 코드가 포함됩니다. 상대방이 이에 대한 응답을 반환하면, WebSocket 연결은 정상적으로 종료됩니다.

### 2-3 WebSocket사용으로 인한 기술적 도전과제

WebSocket은 기존 HTTP의 단방향 통신 구조를 **양방향 통신 구조로 확장해 주는 역할**을 할 뿐, **상태 동기화 자체의 문제를 자동으로 해결해 주지는 않습니다.** 따라서 실시간 협업을 구현하기 위해서는, 통신 계층을 넘어 **상태 동기화 관점에서의 추가적인 도전 과제**를 해결해야 했습니다.

#### 1. 상태관리 문제

WebSocket에서는 클라이언트 상태, 서버 상태, 전송중인 메세지 상태가 전부 독립된 상태를 갖습니다. 로컬의 상태는 나의 변경사항대로 업데이트가 되겠지만, 해당 데이터가 서버에 도착해서 서버의 응답을 대기중 또 다른 사용자가 상태를 수정할 수 있게되면서 문제가 발생됩니다.

#### 2. 메세지 순서 보장 문제

WebSocket은 TCP기반이라 순서가 보장된다고 생각할 수 있습니다. 하지만 그것은 애플리케이션 레벨에서는 보장되지 않습니다. 단일 사용자 기준 프로토콜 레벨까지 보장이 가능하고 여러 클라이언트가 `room`에 있는 상황에서는 어떠한 레벨에서도 순서를 보장할 수 없는 문제가 발생됩니다.

#### 3. 데이터 일관성 문제

해당 문제 근본적인 가장 큰 원인은 바로 **전역 시계**가 없다는 점 입니다. 그렇기 때문에 동시성에 대해서 정의를 할 수 없는 문제가 발생됩니다. 그러면서 각각의 클라이언트가 서로 다른 데이터를 보고있어 데이터의 일관성이 깨지는 문제가 발생됩니다.

## 3. 실시간 동기화 적용

이처럼 WebSocket은 우리에게 양방향통신이라는 길을 열어주었지만 동기화를 위해서는 또 다른 문제들을 해결해야합니다.
하지만 첫 1주 스프린트기간을 가지고 빠르게 기능개발을 해야하는 상황에 페이지 및 Api연동 등 전체 Flow를 만드는것이 디테일한 문제를 해결하는 것 보다 중요하다 판단되어 첫 1주일은 서비스 전체적인 맥락에 중점을 개발하되, 이후 수정을 통해 문제점을 개선하는 방식으로 참여했습니다.

### 3-1. 서버측 적용

`Pub/Sub`패턴을 적용함으로 서버가 연결 관리에 집중할 수 있는 환경을 만들어주고, 메세지가 중앙시스템에 게시(Pub)되고 구독자(Sub)에게 분배되게 됩니다. 이때 서버는 연결관리와 `Pub/Sub`패턴이 올바른 클라이언트에게 전달하는 역활을 하게 됩니다.

```typescript
...
try {
	const roomName = this.getPoiRoomName(data.workspaceId);
	this.validateRoomAuth(roomName, socket);

	// 자신을 제외한 다른 클라이언트에게만 이벤트 전송
	const payload = {
		poiId: data.poiId,
		userId: data.userId,
	};
socket.to(roomName).emit(PoiSocketEvent.POI_HOVERED, payload);
} catch { ... }
...
```

### 3-2. 클라이언트측 적용

낙관적 업데이트를 적용해 메세지를 서버에 보내기 전 로컬 UI를 즉시 업데이트 합니다. 업데이트 후 서버로 메세지가 도착하면 브로드캐스팅을 통해 다른 클라이언트에게 메세지가 전달되고 UI가 업데이트 됩니다.

```typescript

const addSchedule = useCallback(
	(poiId: string, planDayId: string) => {
	// 낙관적 업데이트: 서버 응답 전에 먼저 상태 변경
	setPois((prevPois) =>
	prevPois.map((p) =>
	p.id === poiId
	? { ...p, planDayId, status: 'SCHEDULED' }
	: p
	)
);
...

```

## 4. 구현을 통해 얻은 인사이트

### 4-1. 동시성 테스트에서 들어난 핵심 문제

실시간으로 여행 일정을 편집하는 구조에서 **동시성 이슈**가 가장 핵심적인 문제로 드러났습니다.  
특히 여러 사용자가 동일한 일정과 컴포넌트를 동시에 조작하는 상황에서 **상태 관리 불일치, 메시지 순서 보장 실패, 데이터 일관성 붕괴**가 복합적으로 발생했습니다.

첫 번째로, **메시지 순서가 보장되지 않는 문제**가 명확하게 확인되었습니다.  
예를 들어 클라이언트 A가 `장소1 컴포넌트`를 `DAY1`에서 `DAY2`로 이동시키는 동시에, 클라이언트 B가 동일한 컴포넌트를 `DAY1`에서 `DAY3`으로 이동시키는 상황이 발생했습니다. 이 과정에서 `장소1 컴포넌트`는 `DAY2`를 거치지 않고 곧바로 `DAY3`으로 이동하는 현상이 나타났습니다.  
이는 애플리케이션 레벨에서 요청의 **도착 순서가 보장되지 않은 상태에서 LWW(Last Write Wins) 방식으로 상태를 덮어쓰도록 설계된 구조** 때문이라고 판단했습니다. 결과적으로 마지막에 도착한 요청이 이전 상태를 무조건 덮어쓰면서, 중간 상태가 유실되는 문제가 발생했습니다.

이와 연관된 추가적인 문제로, **네트워크 지연 상황**에서 UX 오류도 확인되었습니다.  
클라이언트 A의 요청이 지연되어 클라이언트 B의 요청에 의해 상태가 먼저 반영된 뒤, 뒤늦게 도착한 A의 요청이 다시 상태를 덮어쓰는 경우가 발생했습니다. 이때 클라이언트 B의 화면에서는 사용자가 UI를 조작해도 상태가 반영되지 않는 것처럼 보이는 현상이 발생했으며, 이는 클라이언트와 서버 간 상태 불일치로 인한 문제로 판단했습니다.

두 번째로, **다수의 사용자가 동시에 컴포넌트를 추가·삭제·이동하는 상황에서 데이터 일관성이 유지되지 않는 문제**가 발생했습니다.  
3명의 사용자가 동시에 임의의 장소를 추가하거나 삭제하고, 일정을 무작위로 변경하는 테스트를 진행한 결과, 특정 `장소 컴포넌트`가 예기치 않게 삭제되거나 생성되는 등 동작이 무작위적으로 나타났습니다. 또한 각 클라이언트마다 서로 다른 UI 상태가 렌더링되며, 사용자가 결과를 예측할 수 없는 UX 문제가 발생했습니다.  
이 문제의 근본 원인은 **전역적으로 사건의 선후 관계를 정의할 수 있는 기준(전역 시계 또는 논리적 순서 체계)이 부재한 상태에서 동시에 발생한 이벤트들을 정렬하지 못했기 때문**이라고 판단했습니다. 그 결과 메시지 순서 문제와 데이터 일관성 문제가 함께 발생했습니다.

세 번째로, `장소 컴포넌트`를 날짜 간(`DAY` ↔ `DAY`) 이동시키는 과정에서 **컴포넌트 UI가 순간적으로 깜빡이는 현상**이 발생했습니다. 이는 상태 변경이 원자적으로 처리되지 않고, 중간 상태가 UI에 노출되면서 발생한 문제로 보았습니다.

마지막으로, **동시에 동일한 장소를 추가하는 경우 중복 처리가 이루어지지 않는 문제**도 확인되었습니다. 여러 사용자가 같은 장소를 동시에 추가하면 중복 검증 없이 동일한 `장소 컴포넌트`가 장소 컴포넌트 보관함에 2개 이상 저장되는 현상이 발생했습니다. 이는 동시 요청에 대한 idempotency와 중복 제어 로직이 부족했기 때문이라고 판단했습니다.

### 4-2. 향후 개선 방향

이러한 문제들을 해결하기 위해,  
 상태 관리 문제와 메시지 순서 보장 문제, 데이터 일관성 문제에 대해서는 **List-CRDT 자료구조와 타임스탬프 기반 LWW Register**를 적용했습니다. 특히 타임스탬프 값이 동일한 경우에는 `타임스탬프 → 버전 → ClientId` 순으로 병합 우선순위를 정의하여 결정 불가능한 상태를 최소화했습니다. 그 외 중복 처리, 네트워크 지연, 패턴 불일치로 인한 문제에 대해서는 연산 단위를 재정의하고 예외 처리 로직을 보강하는 방향으로 개선했습니다.

다음 포스팅시에 문제해결의 대한 내용 보충과 더불어 상황별 동기화 자료구조에 대해 알아보고 각각의 장단점과 구현을 통해 얻은 인사이트를 공유하겠습니다.
